# CommandsCenter 1.0.0

CommandsCenter now runs OpenCode v2 inside the CC process through the embedded
SDK. A separate OpenCode daemon is no longer required.

## Breaking changes and upgrade expectations

- The engine integration uses `@opencode/sdk` 2.0.27. Old daemon connection,
  binary, port and restart settings no longer configure the engine.
- This release does not provide backward compatibility for v1 engine sessions
  or history. Back up an existing installation before upgrading; do not point an
  older CC binary at a workspace already opened by this release.
- Portable specialist configuration, instructions, skills, custom tools, MCP
  definitions, task templates, documents and settings remain workspace-owned.
  Standalone tasks, runtime history and scheduler state are outside workspace-only
  recovery guarantees. Provider authentication and secret values may need to be
  recreated or re-entered on another machine.
- Node.js 24 remains the tested runtime for this release. An upstream OpenTUI
  dependency declares Node >=26.4 and emits an engine warning on Node 24;
  engine-strict installation is not supported by this acceptance. The Node 26 LTS
  upgrade is scheduled separately.

## Preserved features

- Persistent specialist chat, streaming, attachments, system prompts and tool
  permissions use the embedded engine integration.
- Autonomous task execution, custom tools, MCP connections and MCP OAuth remain
  available.
- Interactive terminals use CC-owned `node-pty` sessions. Content search uses
  bundled ripgrep, so no system-installed ripgrep is required.
- Global file search refreshes automatically while open. Newly created filenames
  can still take about ten seconds to appear in the engine's fallback index.
- The stop script authenticates HTTP shutdown with the runtime shutdown secret;
  it no longer requires a browser session for that request.

## Installation and services

Install the release with `npm install -g commandscenter@1.0.0`, then use the
existing `ccenter` setup/start flow. systemd or launchd still supervises CC itself;
removing the separate engine daemon does not remove the CC service.

The SDK and native dependencies are distributed alongside the bundled CLI.
Native dependencies must be installed for the destination operating system and
architecture; copy the workspace, not another machine's `node_modules`.

## Acceptance coverage

The migration was exercised with real local providers and MCPs by the operator,
plus automated local fixtures. Clean installation and service lifecycle checks
passed on macOS arm64 and Ubuntu arm64 with Node 24. Package smoke also covered
Linux amd64 under emulation. Workspace-only configuration recovery and chat,
custom-tool, MCP, search and terminal execution passed across macOS-to-Linux
relocation with a fresh database. Windows acceptance remains unverified.
