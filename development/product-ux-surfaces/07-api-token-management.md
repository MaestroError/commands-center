# Epic 07 — API Token Management

> **Status:** ✅ Done — implemented in commit `842ade7` (token management with scoped bearer auth).

## Overview

Add a new **API** section to the sidebar navigation (positioned before Settings) that gives users a place to manage programmatic access to CommandsCenter. The initial tab is **Tokens** — users can generate named bearer tokens, see them listed with metadata, and revoke them individually.

The page layout mirrors the Settings page exactly: `PageHeader` + `cc-panel` + `TabBar`. A second tab (for public API documentation or configuration) can be added later without structural changes.

On the backend, only a SHA-256 hash of each token is persisted — the raw value is returned once at creation time and never stored. This is the same pattern used by GitHub, npm, and Stripe for opaque API tokens.

---

## Package Decision

**No new package needed.** Node.js built-in `crypto` handles both generation and hashing:

```ts
import { randomBytes, createHash } from "node:crypto";

// Generate a prefixed, URL-safe token
const raw = `cc_${randomBytes(32).toString("base64url")}`;

// Store only the hash — never the raw value
const hash = createHash("sha256").update(raw).digest("hex");
```

The `cc_` prefix makes tokens identifiable in logs and compatible with GitHub's secret-scanning / leak-detection tools. No JWT (hard to revoke cleanly), no external auth library, no added attack surface.

---

## Token permissions (scopes)

Each token carries a set of **scopes** that gate which public-API endpoints it can reach. There are exactly **two persisted scopes**, plus one UI-only convenience:

| Scope       | Persisted?   | Opens                                                                                                                                                                                                                                                    |
| ----------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `templates` | yes          | The three template endpoints from [Epic 08](./08-public-task-api.md): list templates, trigger a template, poll a template run.                                                                                                                           |
| `tasks`     | yes          | Everything in [Epic 09](./09-public-task-api-tasks.md) — direct task create/trigger/schedule, task/run/feedback reads, board-status listing, and the agent/template **discovery** endpoints. (Does _not_ include the template _action_ endpoints above.) |
| **Board**   | no (UI only) | A convenience toggle in the token-creation form that simply switches **both** `templates` and `tasks` on. It is not stored; a token with both scopes is rendered as "Board (full access)".                                                               |

Rules:

- A token must carry the scope a route requires, or the request is rejected with `403 Forbidden` (distinct from `401`, which means the token itself is invalid/revoked).
- The **shared discovery** endpoint `GET /api/public/v1/task-templates` (template id/title/description) is readable with **either** scope, since both template consumers and task consumers need template IDs (task consumers use them to filter tasks by source template). All other template _action_ endpoints remain `templates`-only.
- Scopes are immutable for a token's lifetime — to change them, revoke and re-issue. This keeps the audit trail honest.

The scope set is stored on the token row and returned by `validateToken`, so the guard can enforce it per request.

### Story 1 — DB schema: `api_tokens` table

**Files touched:**

- `packages/backend/src/db/schema/api_tokens.ts` _(new)_
- `packages/backend/src/db/schema/index.ts` _(export new schema)_
- `packages/backend/src/db/migrations/…` _(generated by drizzle-kit)_

**Schema:**

```ts
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const apiTokens = sqliteTable("api_tokens", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  token_hash: text("token_hash").notNull().unique(),
  token_prefix: text("token_prefix").notNull(), // first 12 chars of the raw token — shown in UI for identification
  scopes_json: text("scopes_json").notNull(), // JSON array of scope strings, e.g. ["templates","tasks"]
  created_at: integer("created_at", { mode: "timestamp_ms" }).notNull(),
  last_used_at: integer("last_used_at", { mode: "timestamp_ms" }),
  revoked_at: integer("revoked_at", { mode: "timestamp_ms" }),
});
```

After adding the schema, run:

```sh
pnpm --filter @cc/backend db:generate
pnpm --filter @cc/backend db:migrate
```

**Acceptance criteria:**

- Migration runs cleanly on both a fresh DB and an existing DB with real data.
- `revoked_at IS NULL` means the token is active; a non-null value means revoked (soft delete — preserves the audit trail without exposing the hash).
- `token_hash` has a unique index so a forged duplicate cannot be inserted.
- `scopes_json` stores a JSON array of the persisted scopes (`templates` / `tasks`); a token with neither scope is rejected at creation (a token that can reach nothing is meaningless).

### Story 2 — Backend service: `ApiTokenService`

**File:** `packages/backend/src/services/api-token-service.ts` _(new)_

| Method          | Signature                                                                              | Description                                                                                                              |
| --------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `createToken`   | `(name: string, scopes: ApiTokenScope[]) => { token: string; record: ApiTokenRecord }` | Generates raw token + hash + prefix, persists `scopes_json`, inserts row, **returns the raw value once**                 |
| `listTokens`    | `() => ApiTokenRecord[]`                                                               | All rows (incl. scopes); `token_hash` is never included in the return type                                               |
| `revokeToken`   | `(id: string) => boolean`                                                              | Sets `revoked_at = now()`; returns `false` if id not found                                                               |
| `validateToken` | `(raw: string) => ApiTokenRecord \| null`                                              | Hashes input, looks up where `revoked_at IS NULL`, bumps `last_used_at`, returns record (**including scopes**) or `null` |

`ApiTokenScope = "templates" | "tasks"`.

`ApiTokenRecord` (the public shape — no hash):

```ts
type ApiTokenRecord = {
  id: string;
  name: string;
  token_prefix: string;
  scopes: ApiTokenScope[];
  created_at: Date;
  last_used_at: Date | null;
  revoked_at: Date | null;
};
```

**Acceptance criteria:**

- The raw token value is not logged anywhere inside the service.
- `validateToken` is the only method that updates `last_used_at`, and its returned record exposes `scopes` so the guard can authorize per route.
- All methods are synchronous (better-sqlite3 is sync; no async needed).
- `createToken` throws if `name` is blank or if `scopes` is empty.

### Story 3 — Backend routes: `/api/api-tokens`

**Files touched:**

- `packages/backend/src/routes/api-tokens.ts` _(new)_
- `packages/backend/src/routes/index.ts` _(register new route file)_
- `packages/shared/src/schemas/api-tokens.ts` _(new — shared Zod schemas)_

**Endpoints:**

| Method   | Path                  | Auth                 | Body                                        | Response                                    |
| -------- | --------------------- | -------------------- | ------------------------------------------- | ------------------------------------------- |
| `GET`    | `/api/api-tokens`     | owner session        | —                                           | `{ tokens: ApiTokenRecord[] }`              |
| `POST`   | `/api/api-tokens`     | owner session + CSRF | `{ name: string; scopes: ApiTokenScope[] }` | `{ token: string; record: ApiTokenRecord }` |
| `DELETE` | `/api/api-tokens/:id` | owner session + CSRF | —                                           | `204 No Content`                            |

All three routes go through the existing owner-auth guard unchanged — they are UI-facing routes, not part of the public API.

**Shared Zod schemas** (in `packages/shared/src/schemas/api-tokens.ts`):

```ts
export const ApiTokenScopeSchema = z.enum(["templates", "tasks"]);

export const ApiTokenRecordSchema = z.object({
  id: z.string(),
  name: z.string(),
  token_prefix: z.string(),
  scopes: z.array(ApiTokenScopeSchema),
  created_at: z.number(), // timestamp_ms
  last_used_at: z.number().nullable(),
  revoked_at: z.number().nullable(),
});

export const CreateApiTokenBodySchema = z.object({
  name: z.string().min(1).max(100),
  scopes: z.array(ApiTokenScopeSchema).min(1), // at least one scope required
});

export const CreateApiTokenResponseSchema = z.object({
  token: z.string(),
  record: ApiTokenRecordSchema,
});
```

**Acceptance criteria:**

- `POST` is the only response that ever includes the `token` field.
- `DELETE` returns `404` if the id does not exist.
- `name` is validated as non-empty (max 100 chars) and `scopes` as a non-empty subset of `{templates, tasks}` via Zod at the route level.

### Story 4 — Auth guard: bearer token support for `/api/public/`

**Files touched:**

- `packages/backend/src/lib/owner-auth-guard.ts` _(modify)_
- `packages/backend/src/lib/start-server-runtime.ts` _(inject `ApiTokenService` into `RuntimeContext`)_

The existing session-cookie flow is **not changed**. A new branch is added at the top of the guard for the `/api/public/` namespace (reserved for the future public API):

```
if pathname starts with /api/public/:
  read Authorization: Bearer <raw> from request header
  record = apiTokenService.validateToken(raw)
  if record is null → throw UnauthorizedError("Invalid or revoked API token.")  // 401
  attach record to request (request.apiToken = record)
  requiredScope = scopeForPublicRoute(method, pathname)   // "templates" | "tasks" | "either"
  if requiredScope not satisfied by record.scopes → throw ForbiddenError("Token is missing the required scope.")  // 403
  else → continue (no CSRF check — bearer tokens are not forgeable cross-site)
else:
  existing session + CSRF flow (unchanged)
```

`scopeForPublicRoute` is a small table mapping public paths to their required scope (see the [permissions model](#token-permissions-scopes)): template-action paths → `templates`; task paths → `tasks`; the shared `GET /api/public/v1/task-templates` discovery path → `either`. Keeping it in one table (co-located with the route definitions) means a new public route can't silently ship without a scope decision.

The `ApiTokenService` instance is added to `RuntimeContext` so the guard can reach it. `request.apiToken` is typed via Fastify module augmentation so downstream handlers and audit logging can see the acting token.

**Acceptance criteria:**

- A valid active bearer token **with the required scope** grants access; an authenticated token **without** it returns `403` (distinct from the `401` for invalid/revoked tokens).
- A revoked or unknown token returns `401` with `{ error: "Invalid or revoked API token." }`.
- A request to `/api/public/*` with a valid session cookie but no bearer token is **rejected** (public routes are token-only by design).
- `request.apiToken` is populated for every authenticated public request.
- All existing `/api/` routes (non-public) are completely unaffected — the change is purely additive.
- No CSRF header is required for bearer-authenticated requests.

#### `TokensTab` behaviour

**Token list:**

- Each token card shows: **Name**, **Prefix** (`cc_abc123…` — monospace), **Permissions** (scope badges — see below), **Created** date, **Last used** date (or "Never"), **Status** badge (Active / Revoked).
- Permission display: `Task Templates`, `Tasks`, or — when both scopes are present — a single **`Board`** badge.
- Active tokens have a **Revoke** button.
- Revoked tokens are shown with muted styling and no Revoke button (kept for auditability).

**Create flow:**

1. "Create token" button opens an inline form with a **Name** text field and a **Permissions** group of three toggles:
   - **Task Templates** → adds the `templates` scope.
   - **Tasks** → adds the `tasks` scope.
   - **Board** → convenience only: switching it on turns **both** of the above on; it renders as on when both are on. It is not sent to the backend as a scope — the form submits the derived `scopes` array (`templates` and/or `tasks`).
2. Submit is disabled until a name is entered **and** at least one scope is selected.
3. On submit, calls `POST /api/api-tokens` with `{ name, scopes }`.
4. Response triggers a **one-time reveal panel** showing the full raw token, a **Copy** button (`navigator.clipboard.writeText`), and a dismissal warning: _"This token will not be shown again. Copy it now and store it somewhere safe."_ The panel also restates the granted permissions so the integrator knows the token's reach.
5. Closing the panel clears the raw value from component state — it cannot be re-opened.

**Revoke flow:**

- Clicking **Revoke** opens a confirmation modal (same pattern as `SecretCard`'s delete dialog).
- On confirm, calls `DELETE /api/api-tokens/:id` and invalidates the query.

**API client functions** (in `packages/frontend/src/lib/api.ts`):

```ts
listApiTokens(): Promise<{ tokens: ApiTokenRecord[] }>
createApiToken(input: { name: string; scopes: ApiTokenScope[] }): Promise<{ token: string; record: ApiTokenRecord }>
revokeApiToken(id: string): Promise<void>
```

**Acceptance criteria:**

- The **Board** toggle is pure UI sugar: it sets/reflects both underlying toggles and is never persisted or sent as its own scope.
- Submit is blocked with no scope selected; the backend also rejects an empty `scopes` array (defense in depth).
- Token cards clearly show each token's permissions, collapsing both scopes into a single `Board` badge.
- Raw token is shown exactly once in the reveal panel; closing it removes the value from state.
- Copy button is disabled if the clipboard API is unavailable (graceful degradation).
- Revoked tokens remain visible but clearly distinguished.
- Empty state shown when no tokens exist yet.
- Loading, error, and success states all handled (consistent with other tab components).
