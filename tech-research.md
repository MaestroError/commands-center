# Architectural Blueprint and Technology Stack for an OpenCode Agent Orchestration Platform

## Executive Summary

The engineering of an open-source, container-ready platform designed to orchestrate isolated `opencode` AI agents requires a highly scalable, deterministic, and maintainable technology stack. The system must act as a centralized Node.js-based orchestrator, multiplexing dynamic child processes representing individual agent workspaces, managing real-time full-duplex WebSocket streams for interactive terminal access, and bridging external services via the Model Context Protocol (MCP). Furthermore, the frontend architecture must deliver a low-latency, sophisticated developer experience encompassing a conversational AI interface, a virtualized file system browser, and a fully integrated code editor.

To strictly adhere to the core principles of maximum development velocity and long-term maintainability, the architecture must reject brittle, highly abstracted frameworks in favor of type-safe, explicitly defined, and modular libraries. The overarching design paradigm mandates strict separation of concerns, extensive dependency injection, and comprehensive runtime validation. This report provides an exhaustive, deeply technical analysis and a definitive recommendation for the ideal technology stack, covering the database layer, the backend web framework, the frontend component ecosystem, integration protocols, background job schedulers, and the rigorous quality assurance pipelines required to sustain the platform.

## System Architecture and Pragmatic Layering Principles

The foundation of the orchestration platform relies on a pragmatic separation of concerns, guided by KISS and YAGNI principles. The codebase is structured to isolate the core business logic from the transport and data access layers without introducing heavyweight formal frameworks.

The backend architecture is decoupled into three distinct layers. The Transport Layer contains the routing logic and controllers, responsible purely for parsing incoming HTTP requests and formatting responses. The Domain Layer houses the core business services, encompassing the orchestrator mechanics, the Model Context Protocol routing algorithms, and the background job scheduling logic. Finally, the Data Access Layer isolates the Object-Relational Mapping (ORM) queries, ensuring the business logic remains agnostic to the underlying database engine.

To facilitate testing and modularity, the system leverages Dependency Injection. Services receive their dependencies, such as database connection pools, logging instances, and external API clients, explicitly through their constructors. This inversion of control supports achieving strict code coverage thresholds, as it allows individual components to be unit-tested in isolation using mocked dependencies. This layering is kept lightweight and practical — no formal DDD aggregates, value objects, or domain events are introduced unless a concrete need arises.

Furthermore, TypeScript's static typing, while invaluable during development, provides zero safety guarantees at runtime. Therefore, all data crossing system boundaries must undergo rigorous runtime validation. This includes environment variables parsed on startup, REST API payloads, incoming WebSocket messages from the terminal emulator, and the structured JSON outputs generated by the Large Language Models (LLMs). The platform utilizes Zod for this purpose, defining strict schemas that instantly reject malformed or malicious payloads before they can propagate into the core domain logic, thereby adhering to the principle of failing fast on misconfiguration or invalid input.

## Frontend Engineering: The Agentic Developer Workspace

The frontend requires a highly reactive, component-driven architecture capable of handling complex state synchronization between the conversational AI chat interface, the file system browser, and the integrated terminal emulators. The primary goal is to deliver an experience that mirrors a native desktop Integrated Development Environment (IDE) directly within the browser.

### Core Framework and Build Tooling

The application utilizes React version 19, operating strictly within TypeScript. To optimize both the developer experience and the production build pipeline, Vite serves as the foundational build tool. Vite significantly outperforms legacy bundlers by leveraging native ECMAScript modules during the development phase, providing instantaneous hot module replacement. For production deployments, Vite utilizes highly optimized Rollup configurations to ensure aggressive code splitting and tree shaking. This aligns perfectly with the requirement for lazy loading, ensuring that heavy dependencies, such as the code editor or terminal emulator, are only fetched when the user explicitly requests them.

### UI Component Library and Artificial Intelligence Patterns

Generic component libraries are ill-equipped to handle the specific User Interface (UI) patterns required by conversational AI interfaces. Standard text components fail to smoothly render streaming Markdown character-by-character, and they lack native support for the complex states inherent in agentic workflows, such as collapsible reasoning blocks, tool invocation loading states, and multi-turn message branching.

The recommended approach combines Tailwind CSS for utility-first styling with Shadcn/UI for the component architecture. Shadcn/UI operates on a copy-paste philosophy, meaning the application owns the underlying component code rather than importing it as a black-box dependency. This ownership is critical for modifying components to buffer, parse, and render streaming LLM content without triggering DOM flickering. Furthermore, Shadcn/UI is built upon Radix UI primitives, ensuring that all components are unstyled and highly accessible out of the box, which guarantees ARIA compliance and robust keyboard navigation. For the specific chat interface, the integration of specialized libraries like `assistant-ui`, which natively wrap Shadcn/UI components to handle streaming text, tool call displays, and generative UI patterns, drastically reduces development time while maintaining a polished, professional aesthetic.

### Virtualized File System Browser

The platform requires a robust file manager within the collapsible right panel to allow users to navigate workspaces, read configuration files, and trigger code edits. Building a performant, hierarchical file tree that handles asynchronous data fetching from a backend API while maintaining state across deep directory structures is notoriously complex.

The optimal integration is the SVAR React File Manager component. SVAR provides a truly backend-agnostic architecture through its `RestDataProvider` utility, making it trivial to bind the React component to the Node.js backend's filesystem APIs. Performance is guaranteed through dynamic directory loading and efficient rendering strategies, allowing the component to handle directories with thousands of files without degrading the main browser thread. The component provides a comprehensive feature set out of the box, including breadcrumb navigation, split-views for cross-folder operations, multiple layout modes, and a customizable context menu for executing file operations such as creation, deletion, and renaming.

### Integrated Code Editor and Syntax Highlighting

To fulfill the requirement of allowing users to read and edit files directly from the web interface with comprehensive syntax highlighting, the Monaco Editor, integrated via the `@monaco-editor/react` package, is the industry standard.

Monaco is the underlying engine for Visual Studio Code, providing unparalleled syntax highlighting, IntelliSense, and code formatting for over fifty languages natively. The editor operates on a virtual file system concept using a Model-URI architecture. By associating each opened file from the SVAR file manager with a unique `monaco.Uri`, the editor can maintain an accurate undo stack and provide cross-file IntelliSense capabilities, effectively simulating a real IDE environment within the browser. When integrating Monaco with Vite, the architecture must correctly configure the necessary web workers to process language services asynchronously, ensuring the main UI thread remains unblocked during heavy syntax analysis.

### Interactive Terminal Emulator

A critical feature of the platform is the provision of an interactive global terminal, as well as specific terminal windows tied to each agent's workspace. This requires a sophisticated combination of frontend rendering and backend pseudo-terminal management.

The frontend terminal implementation relies on `xterm.js`. This library utilizes a WebGL and canvas-accelerated renderer, making it capable of handling high-throughput log streams without freezing the Document Object Model (DOM). It is the identical underlying terminal technology used by VS Code, Hyper, and numerous cloud IDEs. To ensure the terminal dynamically resizes in accordance with the browser window or the collapsible side panels, the `xterm-addon-fit` extension is essential. Furthermore, the `xterm-addon-attach` extension simplifies the process of binding the terminal's input and output directly to the WebSocket stream established with the backend orchestrator.

## Backend Orchestration and Application Programming Interface

The backend serves as the nerve center of the platform. It is responsible for proxying HTTP requests to the single OpenCode engine process, managing its lifecycle, and maintaining persistent connections for real-time data streaming.

### Web Server Framework Selection

While Express.js is the traditional default for Node.js applications, Fastify is the unequivocally superior choice for a modern, high-performance AI orchestrator.

The primary advantage of Fastify is its highly optimized tree-routing structure and native support for HTTP/2. This results in significantly higher request throughput and lower latency, which is critical when managing multiple concurrent Server-Sent Events (SSE) and WebSocket streams generated by the AI agents and terminal sessions. Fastify also integrates JSON Schema validation directly at the routing layer. By utilizing Zod combined with the `fastify-type-provider-zod` plugin, the backend achieves end-to-end type safety. Inputs are validated before the execution ever reaches the controller, allowing the server to instantly reject malformed tool calls or Model Context Protocol requests without executing any business logic. Additionally, Fastify provides scoped error handlers via the `setErrorHandler` method, ensuring that uncaught exceptions within deeply nested agent workflows trigger structured, consistent JSON error responses rather than crashing the entire Node.js process silently.

### The Single-Process Orchestrator Pattern

The core requirement dictates that the application manages the `opencode` engine as a single persistent `opencode serve` process, rather than executing on-demand CLI commands. This persistent daemon approach eliminates the multi-second startup latency associated with initializing the models on every message, maintaining active conversation states and file-system watchers continuously.

The Node.js orchestrator utilizes the native `child_process.spawn()` module to launch a single `opencode serve` instance. All agent workspaces are accessed through this one process — workspaces are switched via HTTP headers or query parameters, not by running separate server processes per agent. This eliminates port management complexity, reduces resource consumption, and simplifies lifecycle management. The orchestrator routes requests from the frontend to the single engine, specifying the target workspace context per request.

### Binary Management and the Universal Local Strategy

To ensure zero-friction installation across diverse deployment targets, including Docker containers, global NPM installations, and bare-metal servers, the platform manages the `opencode-ai` CLI strictly as a standard dependency within the orchestrator's central `package.json`.

Relying on standard Node module resolution guarantees that `npm ci` cleanly installs the binary into the orchestrator's local `node_modules/.bin/` directory, preventing the pollution of the host system's global `PATH`. This strategy grants the application total version authority. Because the orchestrator relies on specific Application Programming Interface (API) endpoints exposed by the engine, locking the version as a strict dependency in the central manifest protects the platform from unexpected upstream breaking changes. The orchestrator bypasses the overhead of the `npx` command by resolving the absolute path to the binary and spawning it directly using the Node.js `path.resolve` utility. However, the system provides an escape hatch for power users by respecting a specific environment variable. If defined, the orchestrator bypasses the local `node_modules` path and utilizes the globally provided binary, supporting operators who compile custom forks of the OpenCode engine.

### Pseudo-Terminal and WebSocket Streaming Mechanics

Bridging the frontend `xterm.js` emulator with the underlying host operating system requires the implementation of `node-pty` and a robust WebSocket architecture.

The `node-pty` library forks processes with pseudo-terminal file descriptors. This mechanism tricks command-line applications into believing they are running within a genuine physical terminal, which is strictly required to ensure that interactive CLIs, such as text editors or search utilities, output the correct ANSI escape sequences for coloring and cursor positioning. A WebSocket connection, established via libraries like `ws` or `socket.io`, handles the bidirectional communication between the client and server. Standard HTTP polling or Server-Sent Events are completely insufficient for this use case because terminal interaction demands full-duplex communication to provide immediate, character-by-character keystroke feedback.

Optimizing latency is paramount. Pseudo-terminal processes can generate massive volumes of standard output data rapidly, such as during the execution of dependency installations. Transmitting every single byte individually over the WebSocket creates severe network congestion and forces the React UI to freeze during render cycles. To mitigate this, the backend implements a flow-control buffering strategy. It batches the PTY output into optimized intervals, typically 16 milliseconds, before broadcasting the aggregated chunk to the WebSocket, thereby capping the throughput to a manageable level for the frontend renderer. Furthermore, when the browser window resizes or the user toggles the UI panels, `xterm.js` calculates the new terminal dimensions. These column and row metrics are transmitted over the WebSocket, instructing the backend to execute the `ptyProcess.resize(cols, rows)` method. This guarantees that text wraps correctly and the underlying shell does not inadvertently overwrite previous lines.

### Process Lifecycle Management

Managing child processes requires careful handling to prevent orphaned, or "zombie," processes. If the Node.js orchestrator crashes or initiates a graceful shutdown, the underlying `opencode` engine process, the `node-pty` shells, and any sub-processes they spawned (such as language servers or formatters) must be explicitly terminated to prevent resource exhaustion.

On Unix-based systems, the orchestrator spawns the engine process in a detached state and assigns it a unique process group identifier. Upon termination, sending a kill signal to the negative Process ID (`process.kill(-child.pid)`) ensures the operating system eradicates the entire process tree simultaneously. Conversely, Windows environments handle process trees differently, often leaving intermediary executables running independently. For Windows deployments, the orchestrator tracks child PIDs and explicitly utilizes tree-kill libraries or native system commands to recursively terminate any orphaned instances, guaranteeing a pristine environment upon application exit.

### Agent Tool Management: The Tiered Docker Strategy

Agents frequently require external Command Line Interface (CLI) applications to accomplish their objectives. When orchestrating these agents within Docker containers, the ephemeral nature of the environment dictates that dynamically installed tools are lost whenever the container is rebuilt. To balance security, immutability, and agent autonomy, the platform employs a tiered dependency strategy.

| **Dependency Tier**         | **Mechanism**                                                                           | **Architectural Rationale**                                                                                                                                                                                                                                                                          |
| --------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tier 1: NPM Ecosystem**   | Tools defined in the agent workspace's `package.json` or executed on the fly via `npx`. | Keeps state localized to the `node_modules` directory, making installations environment-agnostic (relying only on the Node.js version) and easily restorable. `package.json` provides deterministic, pinned versions for reproducibility; `npx` covers one-off usage without permanent installation. |
| **Tier 2: Base Image**      | Core dependencies baked into the `Dockerfile`.                                          | Ensures universally required, heavy system packages (e.g., `git`, Python environments) are immediately available without slowing down container initialization.                                                                                                                                      |
| **Tier 3: Startup Scripts** | Persisted initialization commands executed on boot.                                     | Acts as an escape hatch for specific utilities that fall outside the NPM ecosystem, restoring them automatically following a container rebuild.                                                                                                                                                      |

For self-hosting users who prioritize absolute environment freedom over container isolation, the platform fully supports a bare-metal deployment mode, allowing the orchestrator to interact directly with the native host system.

## Database Architecture and Dual-Engine Persistence

The platform necessitates a robust database layer to persist agent configurations, conversation histories, custom tool schemas, and complex automation schedules. The architecture must elegantly support both a lightweight, local installation using SQLite and a highly scalable, distributed cloud deployment using PostgreSQL, without resulting in fragmented or duplicated codebases.

### Object-Relational Mapping: Drizzle

While Prisma has historically dominated the Node.js ecosystem, Drizzle ORM is the strictly superior choice for this architecture, specifically due to its alignment with the principles of minimal abstraction and operational simplicity.

Prisma relies on a proprietary schema language and a heavy, auto-generated Rust query engine that operates as a sidecar process. This level of abstraction frequently generates suboptimal, overly complex SQL execution plans behind the scenes, hindering performance debugging. Conversely, Drizzle ORM is a lightweight, SQL-first framework written entirely in TypeScript. It provides absolute type safety from the initial schema definition down to the final query execution, entirely bypassing the memory and startup overhead associated with background engines.

Crucially, Drizzle solves the dual-database requirement elegantly. Maintaining separate schema files for SQLite and PostgreSQL is an architectural anti-pattern that guarantees divergence. Drizzle's design allows developers to define a single, unified source of truth in TypeScript. The application then programmatically switches between the `drizzle-orm/node-postgres` and `drizzle-orm/better-sqlite3` drivers based on the `DATABASE_URL` environment variable during the initial client instantiation. Furthermore, because Drizzle has zero external dependencies and requires no Rust binaries to compile during the installation phase, it significantly accelerates continuous integration pipelines, reduces Docker build times, and minimizes the final container image footprint.

### Schema Design and Data Integrity

The database schema design adheres to strict immutability principles. Critical tables, such as conversation histories and system audit logs, are structured as append-only ledgers to preserve cryptographic integrity and simplify debugging. Primary keys across all distributed entities utilize Universally Unique Lexicographically Sortable Identifiers (ULIDs) rather than standard auto-incrementing integers. This prevents primary key collisions in distributed cloud deployments and supports the Portable Workspace Rule: the app maintains a continuous dual-write strategy — every write to PostgreSQL is also written to `.cc/local.db` (SQLite) inside the workspace directory. On startup, if no PostgreSQL connection is available, the app seamlessly falls back to this local SQLite DB. This guarantees full portability — move the folder to another machine, run `cc`, and the app resumes with identical state, zero external dependencies on the originating host.

## Background Jobs and Automation Schedulers

The platform features an automations interface where users define scheduled prompts dispatched to specific agents. This functionality demands a highly reliable, persistent job scheduling architecture capable of handling concurrency and rate limiting.

### The Persistence Imperative

Relying on simple, in-memory schedulers such as `node-cron` or `node-schedule` constitutes a critical anti-pattern for production-grade systems. If the Node.js orchestrator restarts due to a deployment, a configuration change, or an unexpected crash, all in-memory schedules are permanently eradicated, leading to silently missed executions. The system unequivocally mandates a persistent, database-backed queueing mechanism.

### Environment-Specific Scheduler Selection

Because the application supports both local and cloud deployments, the architecture abstracts the underlying queueing logic behind a common interface, keeping the implementation straightforward.

| **Deployment Environment** | **Scheduler Technology**       | **Implementation Details** |
| -------------------------- | ------------------------------ | -------------------------- |
| **Cloud (PostgreSQL)**     | `pg-boss` or `graphile-worker` |

Leverages native PostgreSQL `SKIP LOCKED` semantics for highly performant, distributed, exactly-once job execution without requiring Redis.

|
| **Local (SQLite)** | `bree` with SQLite state tracking |

`pg-boss` is incompatible with SQLite. The system uses `bree` for cron syntax parsing and worker threads, coupled with local SQLite tables to track job states and prevent missed executions.

|

The `pg-boss` library is particularly suited for the PostgreSQL environment as it offers built-in support for cron scheduling, priority queues, and advanced rate limiting. This aligns perfectly with the requirement to control the total volume of automations executed per schedule based on global `.env` restrictions.

When an automation job triggers, it must operate in absolute isolation to prevent state contamination with active user sessions. The background worker reads the target agent and the specified prompt from the job payload, gathers the necessary context from the virtual workspace, injects a unique correlation identifier for tracing, and spawns a transient, headless interaction with the `opencode serve` API. The input parameters and the agent's final response are then recorded directly into a dedicated database ledger for future auditing and user review.

## AI Agent Orchestration and Tool Integration

The platform's capability to dynamically equip agents with custom tools and securely connect them to external Application Programming Interfaces (APIs) defines its utility. This requires a robust, standardized integration protocol.

### The Model Context Protocol (MCP)

Anthropic's Model Context Protocol (MCP) serves as the foundational architecture for all tool integration. MCP standardizes communication by strictly separating the concern of providing context and tools from the actual interaction with the underlying LLM.

The Node.js orchestrator implements the official `@modelcontextprotocol/sdk`. The application runs two internal MCP servers — one for user-configured custom tools and one for app-provided tools (including Composio integrations) — communicating over standard input/output (`StdioServerTransport`) or via Server-Sent Events (`SSEServerTransport`). These internal servers dynamically register all custom tools defined by the user within the database, translating user-configured HTTP request builders into standardized JSON schemas.

During the protocol lifecycle, when an agent determines it requires external data, the `opencode serve` engine, acting as the MCP Client, dispatches a `tools/list` JSON-RPC request to the orchestrator's internal MCP server. The orchestrator responds with the complete schemas of all available user-defined and application-provided tools. Crucially, the orchestrator utilizes the MCP `listChanged` capability. If a user modifies a custom tool schema within the web UI, the orchestrator immediately emits a notification event. This forces all active `opencode` agents to refresh their toolsets dynamically, enabling real-time capability updates without requiring a disruptive restart of the agent process.

### Integration Layer and Authentication: Composio

While MCP elegantly handles the standardization of the communication protocol, integrating an agent with hundreds of external APIs, such as GitHub, Jira, or Salesforce, introduces massive engineering complexity. Managing diverse OAuth 2.0 flows, handling token refresh cycles securely, and navigating disparate API rate limits presents an unacceptable maintenance burden.

The platform resolves this complexity by integrating Composio as the unified API and managed authentication layer. Instead of forcing the user to securely manage highly sensitive OAuth tokens and client secrets within local environment variables, the orchestrator integrates the `composio-core` Node.js SDK. Composio provides "Connect Links"---secure, hosted authorization pages where users grant the platform access to their third-party accounts. Once authenticated, Composio assumes total responsibility for securely storing and refreshing the tokens.

Furthermore, the application exposes Composio's capabilities to the OpenCode agents via the internal app-provided MCP server. Per-agent tool access is explicitly controlled by the user: when creating or editing an agent, the user selects which MCP servers and specific tools that agent is allowed to use, and those selections are enforced via OpenCode's `permission` configuration system. In parallel, Composio's "Tool Router" provides intelligent action discovery — instead of bloating the LLM's finite context window by injecting hundreds of individual tool schemas simultaneously, the Tool Router can dynamically search and load the exact Composio action required based on the agent's natural language intent. Both mechanisms coexist: user-curated permissions define the boundaries of what an agent _may_ access, while the Tool Router optimizes _how_ Composio actions are discovered within those boundaries. This architecture guarantees zero-friction maintenance; because Composio completely abstracts the underlying API version changes and authentication mechanics, the burden of maintaining external integrations is entirely offloaded from the core application.

## Code Quality, Testing, and Continuous Integration

To ensure extreme maintainability, mitigate regressions during rapid development cycles, and enforce the platform's architectural principles, the project implements draconian quality assurance protocols enforced automatically via Continuous Integration (CI).

### Linting, Formatting, and Static Analysis

Subjective debates over code style severely drain engineering productivity. To eliminate this, Prettier is strictly enforced for all code formatting. Concurrently, ESLint is configured using the `@typescript-eslint/recommended-requiring-type-checking` ruleset. This ensures strict type boundaries are maintained across the entire codebase.

The repository utilizes Husky and `lint-staged` to implement aggressive pre-commit hooks. These hooks automatically reject any code that fails to meet formatting or linting standards locally, ensuring the main branch remains perpetually pristine. A strict "zero warnings" policy is enforced; any ESLint warning is treated as a hard failure during the CI pipeline. If a specific linting rule is deemed inapplicable in a unique scenario, it must be explicitly disabled via an inline comment containing a detailed justification.

### Testing Frameworks and Coverage Mandates

The project mandates a minimum of 95% code coverage for all utility functions, domain services, and pure UI components.

Vitest serves as the primary unit and integration testing framework. As a Vite-native test runner, it shares the exact identical configuration and transform pipeline as the frontend application, resulting in significantly faster execution times compared to legacy runners like Jest. For coverage reporting, Vitest is explicitly configured to utilize the V8 coverage provider rather than Istanbul. The V8 provider utilizes native Abstract Syntax Tree (AST) based remapping directly from the V8 JavaScript engine. This allows the test suite to execute source files without the overhead of pre-transpilation instrumentation, resulting in vastly improved execution speeds, lower memory consumption, and identical reporting accuracy.

For End-to-End (E2E) testing, the platform utilizes Playwright. Playwright is uniquely suited to simulate the complex, multi-pane user flows required by the application. Test suites programmatically simulate a user opening the integrated terminal, invoking a complex tool via the chat interface, and asserting that the resulting file modifications correctly trigger an update within the SVAR file manager pane.

### Continuous Integration Pipeline

The CI/CD pipeline acts as an impenetrable gatekeeper for the `main` branch. A comprehensive GitHub Actions workflow executes on every single Pull Request, utilizing a sequential, fail-fast execution matrix:

1.  **Dependency Resolution:** Executed using `npm ci` to guarantee deterministic package installation based solely on the lockfile.

2.  **Static Analysis:** Execution of the ESLint suite and strict TypeScript compilation (`tsc --noEmit`) to verify type integrity.

3.  **Unit and Integration Validation:** Execution of the comprehensive Vitest suites.

4.  **Coverage Gate:** The workflow utilizes a custom automated action to parse the resulting `json-summary` output. If the global statement, branch, or function coverage drops below the mandated 95% threshold, the action immediately exits with a non-zero status code, failing the build and actively blocking the merge operation.

5.  **End-to-End Simulation:** Execution of the Playwright suites against a fully containerized, ephemeral instance of the application and its PostgreSQL database.

## System Security and Observability

A platform capable of executing arbitrary code via AI agents requires stringent security boundaries and deep observability.

### Security and Least Privilege

Input validation is enforced at every boundary. The system fundamentally distrusts all data originating from the client UI, external APIs, and user-configured MCP servers. Parameterized queries are universally enforced within the Drizzle ORM layer to eliminate SQL injection vectors. Furthermore, the orchestrator explicitly prevents string interpolation when constructing shell commands for the child processes.

The architecture strictly adheres to the principle of least privilege. Agents and their associated workspace processes operate with the absolute minimum system permissions required to execute their specific instructions. Secrets management is paramount; no API keys or database credentials are ever committed to version control. The application natively supports standard `.env` configurations for local development and integrates with secure secret stores for production deployments. Finally, dependency auditing is automated via `npm audit` within the CI pipeline, immediately blocking merges that introduce critical or high-severity vulnerabilities.

### Performance Monitoring and Graceful Degradation

To track the complex, asynchronous interactions between users, the orchestrator, and the isolated agents, the backend utilizes Pino for structured logging. Pino generates high-performance, strictly formatted JSON logs. Every incoming HTTP request, established WebSocket connection, and agent tool invocation is tagged with a unique Correlation ID. This allows operators to trace execution flow linearly across the entire distributed system.

The Node.js orchestrator implements explicit handlers for `SIGTERM` and `SIGINT` signals to guarantee graceful shutdowns. Upon receipt of a termination signal, the application immediately ceases accepting new HTTP connections. It gracefully drains all existing WebSocket streams and pauses the background cron scheduler. Critically, the orchestrator terminates the single `opencode serve` engine process before allowing the main Node.js process to exit. Failure to execute this exact shutdown sequence results in orphaned binaries consuming host memory indefinitely and locking database resources.
